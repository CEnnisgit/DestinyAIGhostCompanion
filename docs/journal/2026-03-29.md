### Afternoon: Phase 3 Strategic Decomposition

7. **Phase 3 breakdown** — Decomposed the monolithic Phase 3 (People & Tenancy) into 4 sub-phases:
    - **3A:** Data Foundation (Company + User + LmpCredential)
    - **3B:** Authentication (JWT + Argon2 + middleware)
    - **3C:** Authorization (RBAC + query scoping)
    - **3D:** Profile Enrichment (extended fields + mgmt API)

8. **Spec placement matrix** — Mapped all Phase 3 deliverables to `docs/2-during-implementation/DDD/ModuleDesign/` directory structure. Identified stale docs from the old Node.js stack.

9. **Domain architecture** — Discussion about multi-company user relationships. Marcus's father works across 3 companies → system must support one person with multiple memberships. Decision: add new `users` and `company` modules alongside existing `tenant` module.

10. **Phase 3A split** — Agreed to split 3A into two sessions:
    - Session 1: Company enrichment + User entity
    - Session 2: LmpCredential + migration of LL152 text columns

### Evening: Professional Network + Registration Architecture

11. **Phase 3E: Professional Network** — Formalized the networking concept as a new sub-phase:
    - User-to-user connections across company boundaries
    - Job transfer, collaboration, LMP credential sharing
    - 3D and 3E are parallel branches off 3C (independent)
    - Created ADR-0026, vision doc, roadmap doc

12. **Codebase audit for Phase 3A** — Thorough research before writing specs:
    - No Company domain entity exists (just a DB stub)
    - No User entity exists (`actor_user_id` is always `Option<Uuid>`)
    - 3 hardcoded dev UUIDs in API routes
    - Table creation pattern: `ensure_ll152_tables()` with `CREATE TABLE IF NOT EXISTS`
    - Found stale Drizzle reference in PAD ingestion workflow → fixed

13. **Registration + tenancy architecture** — Major design discussion:
    - User-first registration (person signs up, then creates/joins company)
    - Free tier = browse buildings + compliance obligations
    - Paid tier = company features (jobs, clients, dispatch, reports)
    - Multi-company membership via junction table (not direct FK)
    - RLS tenant isolation (rejected database-per-tenant)
    - Invite-only for alpha/beta; connections as growth engine
    - Created ADR-0027, vision doc

### Late Evening: IAM Module Restructuring + Aggregate Design

14. **ADR conflict audit** — Compared ADR-0017 (Independent Plumber Tenancy) against ADR-0027. Found two conflicts:
    - "Company of one" assumption → superseded by user-first model
    - "User holds both roles" → superseded by one role per membership (ADMIN ⊇ TECHNICIAN)
    - Updated ADR-0017 with supersession notes

15. **Module naming decision** — Deep research into existing `tenant` module, CRM/Operations history, and the Tenant Portfolio Research doc. Evaluated four options (tenant, users, iam, org, identity). Decision: **IAM (Identity & Access Management)** — created ADR-0028.

16. **IAM module scaffold** — Renamed `ModuleDesign/Users/` → `ModuleDesign/IAM/`. Updated all cross-references, module map, spec headers.

17. **Aggregate decomposition** — Extracted CompanyMembership from User_Profile into standalone spec. Renamed User_Profile → User_Aggregate. IAM module now follows the established pattern:
    - `Company/Company_Aggregate.md` — Aggregate root (tenant container)
    - `People/User_Aggregate.md` — Aggregate root (person identity)
    - `People/CompanyMembership.md` — Child entity of User

18. **Design review (in progress)** — Began critical review of User aggregate spec. Key finding: User is closer to Client (simple validated CRUD) than to Job (complex state machine with events). The spec had events that nothing consumes and that don't match existing patterns. **Open question: strip events and VOs for alpha, follow Client pattern?** — to be answered tomorrow.
