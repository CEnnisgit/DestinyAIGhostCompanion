# 2026-03-31 — Phase 3C.1 Design Questions Resolved

## Context

Yesterday was a massive design sprint — completed 3B auth specs (spec-complete ✅), fixed workspace drift across roadmaps, and began 3C.1 research. Ended the night with 4 open design questions (Q1-Q4) fully analyzed with three perspectives each. Today picks up where we left off.

## What Got Done

### Morning Session: Resolved All 4 Design Questions

Worked through each question deliberately, one at a time:

**Q1 — RLS Scope + TECHNICIAN UX (ADR-0034)**

- Decided: Simple RLS (workspace isolation ONLY) + app-level role filtering
- TECHNICIANs get unified "My Jobs" view — no workspace switching
- User reviewed ADR-0034, tightened language: hiding workspace switcher is a UX choice not a security boundary
- Added Required Test Coverage section to ADR-0034

**Q2 — Portfolio UNION Query**

- Decided: Single smart `UNION ALL` query with per-workspace role scoping
- Derived access query provides workspace list + roles, UNION arms translate directly
- Natural fit with ADR-0034's "unified view" decision

**Q3 — `assigned_to` Field**

- Decided: Replace `responsible_user_id` with `assigned_to`
- One field, one meaning ("who is dispatched to do the fieldwork?")
- `responsible_user_id` was a premature abstraction from before the auth model existed

**Q4 — ADMIN Submit Findings (ADR-0035)**

- User's other agent conducted NYC LL152 legal research
- Key finding: NYC law governs the official inspection artifact, not internal app workflows
- No statute requiring submit/approve role separation
- Real compliance boundary is at **finalization** (draft → signed report), not role permissions
- Reframed SFR-SRAZ-05 from "Approve/Return" to "Finalize/Sign Report"
- Created ADR-0035 (compliance-boundary-at-finalization)
- Added Discovery 4 (Finalization Boundary) to LL152 workflow docs

### Bonus: Finalization Boundary Principle

The Q4 research surfaced something bigger than the role permission question. The inspection lifecycle has a clear compliance model:

```
Draft (editable) → Finalized/Signed (immutable) → Correction/Addendum (new record)
```

This principle affects the entire LL152 workflow implementation — captured in the LL152 design questions doc for future reference.
